Executive verdict

GO7 is live but not security-production-ready. The product operates at go7.ng with real payments, but critical access-control and payment-trust failures mean a motivated client can forge paid status, mutate fees/earnings, and access cross-tenant data. Treat P0 as urgent production hardening.
  1. Rotate Paystack sk_live + Infobip; scrub repo/history
  2. Auth-gate or remove open money CFs (verifyPayment, backfillPayment, updateOrderOnPaymentVerification, agent earnings)
  3. HMAC on onPaystackTransferUpdate
  4. Stop client paymentStatus: paid — server verify + amount bind
  5. debitWalletForDelivery: ignore client fee; server fare
  6. Remove Firestore catch-all; lock bookings/orders fields + transitions
  7. CF-only vendor/rider balances; field denylist
  8. Deploy participant chat rules; scope rider updates to assigned
  9. users get own/admin only; lock addresses; Storage proof party-only
  10. Scheduled Firestore export + restore runbook; enable Sentry

36. Final Q&A

  1. Production-ready? NO for security. YES as a running product with known critical risk.
  2. Key vulns? Catch-all rules; open money CFs; client paid/fee; unsigned transfer webhook; leaked secrets; open chats; balance self-writes.
  3. Incomplete? State machine; immutable audit; DR; App Check; CI; Sentry; rules tests; agent Auth.
  4. Unauthorized access? Cross-customer users/bookings/chats; any-rider orders; vendor self-balance; open admin CFs.
  5. Client money/status? YES.
  6. Firestore rules secure? NO.
  7. Paystack webhooks? Wallet YES (HMAC+idempotent). Transfer NO. Legacy verify NO.
  8. Secrets protected? NO.
  9. Location reliable? BookDelivery mostly yes; TrackDelivery demos undermine trust.
  10. Rider nav ready? Android SDK yes; GPS spoof via rules; web tracking mixed.
  11. Logging / monitoring / DR / tests? All insufficient.
  12. Must fix? Entire P0 list.
  13. After? CI, Sentry, DR drills, App Check, status unification, pagination, docs.
